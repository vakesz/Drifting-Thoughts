# Drifting Thoughts

## Project Snapshot

- **What**: Minimalist micro-journaling and poetry iOS app. Write a thought, style it as a card, share it as an image.
- **Stack**: Swift 6, SwiftUI, SwiftData, XcodeGen. iOS 18.0+ deployment target.
- **Architecture**: Lightweight MVVM. Views read via `@Query`, ViewModels (when present) handle writes via `ModelContext`.
- **Constraints**: No external dependencies, no backend, no accounts. Everything on-device.
- **Concurrency**: Swift 6 strict concurrency (`complete` mode). All ViewModels are `@MainActor`.

## Command Output Handling

- Ignore all LSP errors. The Xcode project is generated by XcodeGen and LSP diagnostics are unreliable until `make generate` is run.
- Always validate correctness with `make build`, not LSP.
- Warnings are treated as errors (both `GCC_TREAT_WARNINGS_AS_ERRORS` and `SWIFT_TREAT_WARNINGS_AS_ERRORS` are `YES`).

## Non-Negotiable Rules

- Run `make format-lint` before every commit (SwiftLint auto-fix + check)
- No Combine (`import Combine` is a lint ERROR via custom rule `no_combine`)
- No `print()`, `debugPrint()`, `NSLog()` (lint warning via custom rule `no_print`; use `os.Logger`)
- No `force_cast` or `force_try` (lint ERROR). `force_unwrapping` is a warning
- No external dependencies, Apple frameworks only
- No repository layers, service layers, API clients, or caching abstractions; direct SwiftData access
- Never edit `.xcodeproj` directly; it is generated from `project.yml` by XcodeGen
- Use `@Observable` / `@Bindable` / `async-await`; never `ObservableObject`, `@Published`, `@StateObject`, `@ObservedObject`, `DispatchQueue`, or completion handlers
- Sorted imports (enforced by SwiftLint `sorted_imports`)
- Trailing commas mandatory in multi-line collections (enforced by `trailing_comma`)
- Attribute placement enforced: `@Environment`, `@State`, `@Binding`, `@Bindable`, `@Query` on same line; `@MainActor`, `@Observable`, `@ViewBuilder`, etc. on line above
- Never add Co-Authored-By or attribution lines to commits
- Imperative mood, sentence-case commit messages (e.g., "Add dark mode toggle"). No conventional commit prefixes

## Architecture

```text
User taps → SwiftUI View (@Query reads) → ViewModel (@Observable, writes) → ModelContext → SwiftData
                                      ↑                                           |
                                      └───────────── @Query auto-refresh ─────────┘
```

```text
DriftingThoughtsApp (@main)
  └─ ContentView (onboarding gate + TabView)
       ├─ Tab: ComposeView → CardDetailView (preview + save)
       ├─ Tab: TimelineView → CardDetailView (view existing)
       └─ Tab: SearchView → CardDetailView (view existing)
```

### When to Use a ViewModel

Only `CardDetailView` uses a full ViewModel (`CardDetailViewModel`) because it manages draft state, style/font selection, image export, and save logic. All other views are simple enough to be view-only with inline `@State` and `@Query`. Follow this principle: **add a ViewModel only when the view has write logic or complex state that would clutter the view**.

### Forbidden Layer Violations

- Views must never import or use `ModelContext` for reads; use `@Query`
- No intermediate repositories or services between ViewModel and SwiftData
- `AppSettings.shared` is accessed directly; never inject or wrap it

### Placement Rules

- New features go in `Features/<Name>/` with `<Name>View.swift` and optionally `<Name>ViewModel.swift`
- Shared UI components and design tokens go in `Core/DesignSystem/`
- Data models go in `Core/Models/`
- App-wide settings go in `Core/Settings/`
- Colors are defined in `Resources/Assets.xcassets` and accessed via `Color("name")` extensions

## ViewModel Pattern

When a ViewModel is needed, follow this template (derived from `CardDetailViewModel`):

```swift
import Foundation
import SwiftData

@MainActor
@Observable
final class <Name>ViewModel {
    // Published state
    var someProperty: SomeType

    init(/* parameters */) {
        self.someProperty = /* initial value */
    }

    func save(in context: ModelContext) {
        // Write to SwiftData via context
    }
}
```

The owning view holds it as:

```swift
@State private var viewModel: <Name>ViewModel
```

## Theme System

The card theming pipeline resolves visual properties for rendering `CardView`:

```text
CardStyle (midnight/parchment/sunset) ─┐
CardThemeOverrides (per-thought fonts) ─┼─→ CardThemeResolver.resolve() → ResolvedCardTheme
AppSettings (watermark, author prefs) ──┘
```

- `CardStyle` — visual style enum with `MeshGradient` colors from the asset catalog
- `CardFontStyle` — typography enum (serif/rounded/monospaced/classic) mapped to `Font.Design`
- `CardThemeOverrides` — `Codable` struct stored on `Thought.themeOverrides`; nullable font overrides
- `CardThemeResolver` — static resolver merging style defaults + per-thought overrides + settings into `ResolvedCardTheme`
- Default style: `.sunset`. Default font: `.serif`

## Settings System

`AppSettings` is a `@MainActor @Observable` singleton with `private init()`. Each property persists to `UserDefaults` via `didSet`. Keys follow the pattern `drift.<module>.<property>`.

Current settings: `showWatermark`, `authorName`, `showAuthorOnCard`, `hasCompletedOnboarding`, `streakFrequency`.

`StreakFrequency` enum (daily/weekly) lives in the same file (`Core/Settings/AppSettings.swift`).

## Naming Conventions

- **Files**: `<Feature>View.swift`, `<Feature>ViewModel.swift`
- **Types**: PascalCase. Caseless enums for namespaces (`enum DriftLayout { static let ... }`)
- **Properties/methods**: camelCase
- **UserDefaults keys**: `drift.<module>.<property>`
- **Enums with options**: conform to `String, CaseIterable, Identifiable, Sendable`
- **MARK comments**: `// MARK: - Section Name` to separate view body sections

## Error Handling

- `try?` with optionals; never `try!`
- `guard let` for early returns
- `??` for safe fallbacks
- No custom error types; no throwing functions in the codebase
